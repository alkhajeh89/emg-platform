# ADR-038 Capability Verification — Test Environment Specification

## Isolation

A second, fully independent Keycloak 25.0 container — own Docker Compose
project (`emg-adr038-verification`), own container name
(`emg-adr038-verification-keycloak`), own network
(`emg-adr038-verification-net`), own port (`8180`, not the shared
`emg-keycloak`'s `8080`), own realm (`emg-verification`, not `emg`), own
throwaway named volume. Defined in
`tests/security/adr_038/docker-compose.verification.yml`. It shares nothing
— no network, no realm, no client, no data — with the running shared dev
stack, and it holds no product code and no persistent product data.

## Required actors — as provisioned

| ADR-038 role | Realm identity | Notes |
| :--- | :--- | :--- |
| Human Principal A | user `human-principal-a` | `tenant_id=tenant-verification-a`, `classification_clearance=CONFIDENTIAL`, roles `platform-user, investigator` |
| Human Principal B | user `human-principal-b` | `tenant_id=tenant-verification-b`, `classification_clearance=INTERNAL`, roles `platform-user, decision-maker` — deliberately a *different* tenant and a *lower* clearance than A, to make substitution/elevation attempts observable |
| Confidential Acting Service (test BFF) | client `emg-verification-bff` | Confidential, service account, client-credentials capable, **granted** token-exchange permission by `provision.py` |
| Unauthorized Acting Service | client `emg-verification-bff-unauthorized` | Structurally identical to the above, **deliberately never granted** exchange permission |
| Downstream Audience A | client `emg-verification-audience-a` | Bearer-only, exists solely as an exchange target and an independent-validation anchor |
| Downstream Audience B | client `emg-verification-audience-b` | Same, second independent audience, used to prove single-audience restriction |

Two supporting identities, both explicitly justified rather than incidental:

- `emg-verification-ropc` — confidential, ROPC-only client used solely to
  obtain a Human Principal token. ADR-035 D-2 explicitly reserves ROPC for
  "service and test purposes"; this is exactly that, never a browser path.
- `emg-svc-knowledge-graph-writer` — an isolated-realm client whose
  **client_id string** intentionally matches a production
  `emg_audit_service.authn._RECOGNIZED_CLIENTS` entry. Required because
  that allowlist is hardcoded, reviewed production code this verification
  may not modify; reusing the id (own random, non-committed secret, isolated
  realm) is the only way to exercise the real, unmodified audit-ingest path
  end-to-end. See `04_FINDINGS_AND_EXTERNAL_CONCERNS.md`.

## Required identity context — as projected into tokens

All via realm `clientScopes`/protocol mappers (`realm/emg-verification-realm.json`):

- `tenant_id` — user-attribute mapper for humans, hardcoded-claim mapper for
  the audit-producer service identity.
- `classification_clearance` — same pattern, mirrors ADR-026 Part E's
  human-side protocol-mapper requirement.
- `realm_access.roles` — standard realm-role mapper, mirrors production
  `authn.py`'s convention.
- `sub` — human subject; required an explicit
  `oidc-usermodel-property-mapper` on the **audience** clients' default
  scopes (see `02_KEYCLOAK_VERIFICATION_CONFIG.md` for why).
- Bounded credential lifetime — `accessTokenLifespan: 60` at the realm
  level, `access.token.lifespan: "60"` per confidential client.

## Secret hygiene

No committed file contains a usable secret:

- `realm/emg-verification-realm.json` declares clients and users with **no
  `secret` field and no `credentials` block at all** — verified by grep
  before finishing (`grep -i secret realm/emg-verification-realm.json` →
  zero matches). Keycloak auto-generates a placeholder secret on import;
  every one is immediately regenerated by `provision.py`.
- `tests/security/adr_038/.env.verification.local` — generated by
  `generate_env.sh` (random 24-byte hex per credential) and further
  populated by `provision.py` (regenerated client secrets, fresh human
  passwords) — is listed in `tests/security/adr_038/.gitignore` and
  confirmed untracked (`git check-ignore -v` and `git status` both
  confirmed it is not staged).
- `docker-compose.verification.yml` requires every credential via
  `${VAR:?set in .env.verification.local}` — the container refuses to start
  without the env file; there is no committed default a workflow could
  silently reuse.

## Reuse discipline for this resumed session

The isolated Keycloak container and its provisioned realm/clients/secrets
from the original run were found still running and healthy
(`docker ps`, `docker compose ls`) and were reused as-is — `provision.py` is
idempotent by design and was not re-run destructively; the environment was
not torn down and recreated.
