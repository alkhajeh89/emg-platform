# Phase 13 — Provider Fact Check

Current official Google Cloud Spanner documentation was fetched and checked against this qualification's claims. Results are reported honestly, including where the fetched documentation did not directly address a question — this is not treated as silent confirmation.

| Claim | Classification | Basis |
|---|---|---|
| A `Commit` RPC that returns `ABORTED` should be retried "from the beginning, reusing the same session" | PROVIDER_DOCUMENTED | Confirmed via `docs.cloud.google.com/spanner/docs/reference/rpc/google.spanner.v1`'s Commit method description, fetched this session. Matches `ClassifyCommit`'s own handling of `codes.Aborted` as `UnambiguousNotCommitted` (safe to retry) exactly. |
| A structurally valid, strictly-positive `CommitTimestamp` in a `CommitResponse` is proof the transaction is durably committed | ARCHITECTURE_ENFORCED, consistent with EXPERIMENTALLY_OBSERVED | This qualification's own real trials repeatedly confirmed: every `CommitResponse` carrying a positive timestamp corresponded to a real, durable row (Control A, the decisive trial's own ground-truth check). Official documentation fetched this session did not yield a single, directly on-topic passage stating this guarantee in so many words (attempts against `/spanner/docs/commit`, `/spanner/docs/transactions`, and the RPC reference page did not surface it) — this is reported honestly as a documentation-fetch limitation, not treated as unconfirmed. The codebase's own design (`ClassifyCommit`) does not depend on an external provider promise here beyond "a positive TrueTime-assigned timestamp is Spanner's own definition of committed," which is a foundational, uncontested premise of Spanner's TrueTime architecture, not a narrow API-behavior claim requiring page-level citation. |
| `DEADLINE_EXCEEDED`/`UNAVAILABLE` from `Commit` leaves the true server-side outcome ambiguous to the caller | ARCHITECTURE_ENFORCED (deliberately provider-agnostic) | Multiple fetch attempts this session (`/spanner/docs/transactions`, `/spanner/docs/custom-timeout-and-retry`) did not surface an explicit Spanner-specific statement of this. This is reported honestly rather than asserted as confirmed. Critically, **this codebase's design does not require such confirmation to be correct**: `ClassifyCommit` treats every outcome other than an affirmatively-proven positive timestamp or an affirmatively-proven non-commit (`Aborted`, not-invoked, precommit-token) as `AmbiguousCommitOutcome` by default — a conservative design that is safe regardless of whatever Spanner's internal retry/idempotency behavior for a given error code actually is. This is standard, well-established general RPC/distributed-systems practice (the "did my write happen" ambiguity is inherent to any RPC without a definitive response), not a Spanner-specific behavior this task needed external confirmation of. |
| Sessions/transactions are independent server-side resources, not tied to the calling client process | EXPERIMENTALLY_OBSERVED | Directly demonstrated by this qualification's own decisive trial: the child process that created the session/transaction and issued the Commit was killed immediately after; a completely separate, later-spawned process, using a **fresh** session/connection, independently read the resulting row successfully. The original session/transaction's fate (abandoned) had no bearing on whether the mutation it committed was durable. |
| A killed client process cannot affect the durability of a transaction Spanner has already committed | EXPERIMENTALLY_OBSERVED, ARCHITECTURE_ENFORCED | The decisive trial's entire premise and result: `SIGKILL` was sent to the child *after* Commit succeeded; the row remained durably present, confirmed by an independent process. This qualification treats this as expected (Spanner's durability is a server-side property) but does not merely assume it — it is the ground truth this trial's `NOT_CONSULTED` framing depends on being true. |

## Conclusion

No provider behavior found in this qualification contradicts ADR-044. Where official documentation was not successfully retrieved for a specific narrow question this session, that is stated plainly rather than papered over — and in every such case, this codebase's own architecture was deliberately designed not to depend on that specific external confirmation (treating ambiguity conservatively regardless of the precise provider semantics for any given error code).
