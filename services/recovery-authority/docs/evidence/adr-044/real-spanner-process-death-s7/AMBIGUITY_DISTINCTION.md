# Phase 11 — Process Loss vs. Ambiguous Commit: Two Distinct Cases

**Case 1 (S7's target, qualified by this task): process loss after an UNAMBIGUOUS success.** The provider response unambiguously proves the Commit succeeded (a structurally valid, strictly positive `CommitTimestamp`, no error) — `ClassifyCommit` returns `UnambiguousSuccess` with certainty. The failure is that the *accepting process* then dies before it can complete the second, separate step (building and durably witnessing the signed `CommittedPayload`). The Spanner-side outcome was never in doubt; the acceptance-provenance chain was lost to a process boundary. Fails closed via `TransitionOnWitnessOutcome(false) → StateUnresolvablePreparedOperation → NEW_EPOCH_REQUIRED`, exactly as this task's decisive trial demonstrates.

**Case 2 (already qualified in Wave 1 Track A, not re-qualified by this task): the provider Commit outcome itself is ambiguous.** No positive proof of success is ever obtained — a transport failure, a deadline exceeded, an unrecognized response shape. `ClassifyCommit` defaults to `AmbiguousCommitOutcome` (its documented, deliberate default for "anything not affirmatively classified" as success or explicit non-commit). Fails closed via `TransitionOnCASOutcome(AmbiguousCommitOutcome) → StateUnresolvablePreparedOperation → NEW_EPOCH_REQUIRED` — the same terminal governance outcome, reached by a different route, at a different point in the sequence (before, not after, provenance would have been established).

**Both fail closed to the same governed outcome, for different reasons, at different points.** This task does not claim Case 1's qualification closes Case 2 — Case 2 was already independently, separately qualified by Wave 1 Track A's `DeadlineInterruption` real-cloud subtest (re-confirmed still passing as part of this task's full validation). Conflating the two would overclaim: Case 1 is about losing an already-established truth; Case 2 is about never establishing one in the first place.
