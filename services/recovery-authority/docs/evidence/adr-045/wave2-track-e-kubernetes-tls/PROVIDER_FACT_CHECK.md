# Provider Fact-Check (Phase 13)

| Claim | Verified | Method |
|---|---|---|
| GKE Dataplane V2 (`ADVANCED_DATAPATH`) enforces `NetworkPolicy` natively (Cilium-based), no separate CNI install needed | Yes | `gcloud container clusters describe` (`datapathProvider: ADVANCED_DATAPATH`) + extensive empirical enforcement throughout this qualification (default-deny genuinely blocks all untested paths; every explicit allow rule genuinely permits exactly its scope) |
| `fsGroup` changes a mounted Secret volume's group ownership so a non-root runtime user can read it via the group-read bit, without requiring a looser `defaultMode` | Empirically confirmed | `FSGROUP_DEFECT.md` — a `WebFetch` against `kubernetes.io` returned content claiming the opposite (Secret volumes "exempt" from `fsGroup`); this was contradicted by direct empirical testing on the real cluster and discarded as unreliable. The real cluster's own behavior is the authoritative source here. |
| Kubernetes `ipBlock` egress rules do not match in-cluster-addressed traffic (Service ClusterIPs or raw pod IPs) on this cluster/dataplane configuration, at any CIDR breadth | Empirically confirmed, reproducible across 4 independent trials (real ClusterIP, real pod IP, a fresh disposable Service's ClusterIP, and an unrestricted `0.0.0.0/0`) | `DNS_NETWORKPOLICY_DEFECT.md`. Reported as an observed behavior of this qualified cluster, not asserted as universal Cilium/GKE Dataplane V2 behavior — no official documentation was found confirming or denying this exact scenario. |
| A cross-namespace combined `namespaceSelector`+`podSelector` egress rule can fail to permit Service-ClusterIP-directed traffic, while `namespaceSelector`-alone (same scope) and same-namespace `podSelector`-alone both succeed | Empirically confirmed via a controlled, isolated diagnostic matrix | `DNS_NETWORKPOLICY_DEFECT.md`. Same caveat: reported as observed behavior of this cluster/configuration, not a general claim about GKE Dataplane V2 or Cilium. |
| NodeLocal DNSCache, when deployed with `-setupiptables=false` and `hostNetwork: false`, does not intercept ClusterIP-addressed DNS traffic | Confirmed via direct pod-spec inspection (`kubectl get pod ... -o jsonpath`) | Ruled out as a contributing factor to the DNS defect |
| GKE metadata server (`169.254.169.254`) is a fixed link-local address, safe to allow by static `ipBlock` unlike dynamic Google API IPs | Well-established, standard GKE/WIF architecture; consistent with this repository's own Track D findings | Track D evidence + this task's own egress design (`NETWORKPOLICY_MATRIX.md` Phase 9) |
| Plain Kubernetes `NetworkPolicy` cannot express FQDN-scoped allow rules for external Google APIs (Spanner/GCS/KMS) | Well-established Kubernetes NetworkPolicy API limitation (the upstream API has no FQDN/hostname-based selector) | Reported honestly as a standing limitation rather than solved with a brittle static IP range — `NETWORKPOLICY_MATRIX.md` Phase 9 |
| TLS certificate/key material loaded via `tls.LoadX509KeyPair` at process startup is not live-reloaded on file change | Confirmed both by source reading (`internal/authority/lifecycle/tls.go`) and empirically (patching the live Secret had no effect on the already-running pod) | `RESTART_FAILURE.md` |
| Kubernetes Secret volumes are always mounted `root:root` regardless of `defaultMode`'s permission bits | Empirically confirmed | `FSGROUP_DEFECT.md` |

## Conclusion

No real provider behavior found in this qualification contradicts ADR-044 or ADR-045. Two genuine defects were found in the *repository's own* landed manifests (not in GKE/Kubernetes itself) and were fixed, regression-tested, and requalified. Both defects existed only because no prior wave had ever exercised real Kubernetes deployment or real NetworkPolicy enforcement — exactly the gap Track E was authorized to close.
