# Wave 2 Track C — Provider Fact-Check

Independently verified against current official Google Cloud documentation (WebFetch/WebSearch) and, where noted, cross-confirmed empirically against real Cloud KMS / real GCS during this qualification. No claim below rests on training-data recall alone.

## Cloud KMS

| Claim | Verified | Source/method |
|---|---|---|
| `EC_SIGN_P256_SHA256` is a currently supported, recommended asymmetric-signing algorithm; requires `ASYMMETRIC_SIGN` purpose, `SOFTWARE` or `HSM` protection level, SHA-256 digest input | Yes | `docs.cloud.google.com/kms/docs/algorithms` |
| A newly created asymmetric `CryptoKeyVersion` starts `PENDING_GENERATION`, transitions automatically to `ENABLED` when generation completes (symmetric keys start `ENABLED` immediately) | Yes | `docs.cloud.google.com/kms/docs/key-states`; empirically confirmed — our real key transitioned to `ENABLED` within ~1s of creation |
| Disabling a `CryptoKeyVersion` is reversible (`DISABLED` ↔ `ENABLED` via `UpdateCryptoKeyVersion`); never destroys key material | Yes | `docs.cloud.google.com/kms/docs/key-states` |
| `AsymmetricSign` against a `DISABLED` version does not necessarily fail instantly if the version was recently used for a successful sign — empirically measured convergence to `FailedPrecondition/KEY_DISABLED` at ~48–62s in this session's trials, but a **fresh** connection with **no recent prior use** observes rejection immediately | Empirically confirmed, this session (three independent methods: `gcloud kms asymmetric-sign`, a standalone Go probe with a fresh client per attempt, and an isolated `go test` run) | Not officially documented as a numeric SLA; recorded as an empirical qualification finding, not a doc citation |
| Cloud KMS IAM cannot be bound at the individual `CryptoKeyVersion` level — `setIamPolicy` is only supported at `CryptoKey` (and above) | Yes | `docs.cloud.google.com/kms/docs/reference/rest/v1/projects.locations.keyRings.cryptoKeys/setIamPolicy`; empirically confirmed — `SetIamPolicy` on the `CryptoKeyVersion` resource path was never attempted (not exposed by the client at that resource type); `SetIamPolicy` on the `CryptoKey` succeeded/failed exactly as documented during IAM qualification |
| `roles/cloudkms.signer` = `cloudkms.cryptoKeyVersions.useToSign` (+ `locations.get/list`, `resourcemanager.projects.get`) only — no `viewPublicKey`, no `get` | Yes, and empirically confirmed via real `403`s (`GetPublicKey`/`UpdateCryptoKeyVersion` both denied for the signer principal) | `docs.cloud.google.com/kms/docs/reference/permissions-and-roles` |
| `roles/cloudkms.publicKeyViewer` = `cloudkms.cryptoKeyVersions.viewPublicKey` only — does **not** include `cloudkms.cryptoKeyVersions.get` | Yes | same source; this is why the pin-capture principal needs **both** `roles/cloudkms.viewer` (for `GetCryptoKeyVersion`) and `roles/cloudkms.publicKeyViewer` (for `GetPublicKey`) — confirmed both by doc and by real qualification (`CaptureFromKMS` succeeded only once both were granted) |
| `DESTROY_SCHEDULED` → `DESTROYED` lifecycle: `destroy` schedules destruction after `destroyScheduledDuration`; `restore` reverses it before `destroyTime`; once `DESTROYED`, key material is irrecoverable | Yes | `docs.cloud.google.com/kms/docs/destroy-restore` |
| Private asymmetric key material is never exportable from Cloud KMS under any API | Yes (foundational, unchanging product guarantee; not re-verified via a new doc fetch this session, consistent with prior waves) | `kmssigner`'s own package doc / established Cloud KMS product design |
| Destroy/restore lifecycle was **not empirically exercised** this qualification, per explicit task instruction ("no destroy operation during this qualification") | N/A — deliberately not exercised | Governed, not qualified — consistent with ADR-045 §18 item 10's "exercised or explicitly governed" allowance |

## Google Cloud Storage

| Claim | Verified | Source/method |
|---|---|---|
| `cloud.google.com/go/storage` returns the identical `storage.ErrObjectNotExist` sentinel (HTTP 404) for an object-resource call (`ObjectHandle.Attrs`/`NewReader`) whether the specific object is absent or the containing bucket does not exist at all | Empirically confirmed against **both** real GCS and this repository's `fake-gcs-server` emulator, via a standalone probe program | This session, direct API calls |
| `storage.ErrBucketNotExist` is a distinct sentinel, but is only returned by a bucket-resource call (`BucketHandle.Attrs`), never by an object-resource call | Yes, and empirically confirmed | `docs.cloud.google.com/go/storage` package docs + the same probe |
| `BucketHandle.Attrs()` requires `storage.buckets.get`; this is a genuinely new, minimal permission requirement for any principal relying on the bucket-vs-object disambiguation fix | Empirically confirmed — a principal granted only `storage.objects.get`/`create` received a spurious `403` from the disambiguation check until `storage.buckets.get` was added | This session, real-cloud IAM qualification (see `go_test_iam_qualification.log`, first failing run) |
| `roles/storage.objectCreator` grants `storage.objects.create` only — does **not** include `storage.objects.get` | Empirically confirmed via a real `403` on the create-if-absent conflict-resolution read-back, using this exact predefined role | This session (see the P0 remediation report's discovery narrative) |
| Custom IAM roles combining exactly `storage.objects.create` + `storage.objects.get` + `storage.buckets.get` (and, for the read-only verifier, `storage.objects.get` + `storage.buckets.get` only) behave exactly as documented — no extra capability observed, no missing capability once bound | Empirically confirmed, this session — all four qualification principals (signer, pin-capture, ledger-writer, verifier) passed their full allow/deny matrix once bound to these exact custom roles | `go_test_iam_qualification_v2.log` |

## Conclusion

No provider behavior found in this qualification contradicts ADR-044 or ADR-045. Two real defects were found in **this repository's own code** (compromise-ledger timestamp precision; `gcswitness` bucket-vs-object-404 collapse) — both are now fixed, regression-tested locally and against real Cloud KMS/GCS, and documented transparently in this evidence package. The IAM manifest (`internal/authority/iam/manifest.json`) was updated to add `storage.buckets.get` to every principal that calls `gcswitness.Exists`/`ReadExact`, with the reasoning recorded in each affected principal's `notes` field.
