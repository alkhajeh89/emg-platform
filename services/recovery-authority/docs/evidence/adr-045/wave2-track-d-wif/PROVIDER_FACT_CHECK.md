# Track D — Provider Fact-Check (GKE Workload Identity Federation)

Independently verified against current official Google Cloud/GKE documentation, and cross-confirmed empirically against the real `emg-staging` cluster during this qualification.

| Claim | Verified | Source/method |
|---|---|---|
| GKE creates one workload identity pool per project (`PROJECT_ID.svc.id.goog`); every KSA in every cluster in that project is a federated principal inside it | Yes | `docs.cloud.google.com/kubernetes-engine/docs/concepts/workload-identity`; empirically confirmed — `workloadIdentityConfig.workloadPool = emg-platform-staging.svc.id.goog` on the real `emg-staging` cluster |
| Member format `serviceAccount:PROJECT_ID.svc.id.goog[NAMESPACE/KSA_NAME]` uniquely identifies one KSA | Yes, empirically confirmed | Real `roles/iam.workloadIdentityUser` bindings using this exact format worked; a same-named KSA in a different namespace, or a different KSA name in the same namespace, both correctly failed real token issuance despite either sharing the identical `iam.gke.io/gcp-service-account` annotation |
| A KSA without the `iam.gke.io/gcp-service-account` annotation is still a recognized identity in the pool (`PROJECT_ID.svc.id.goog`) but cannot obtain GCP credentials for any GSA | Yes, empirically confirmed | The default KSA's metadata-server `/email` resolved to the bare pool identity (`emg-platform-staging.svc.id.goog`, not a GSA email); it received an OAuth token as *that* pool identity but that identity holds zero IAM grants anywhere, so every subsequent privileged call failed |
| `roles/iam.workloadIdentityUser` is required and sufficient for the base KSA→GSA token-issuance flow | Yes, empirically confirmed | Both qualification GSAs authenticated correctly with only this one role bound; no other role was needed for ordinary token issuance |
| `roles/iam.serviceAccountTokenCreator` is **not** required for the base WIF mechanism | Yes, empirically confirmed | Never granted to either qualification GSA; base identity/token issuance and the real `AsymmetricSign` call both worked without it. (It IS required for a *different*, explicit impersonation flow, e.g. `gcloud ... --impersonate-service-account`, which this task deliberately never granted either — every impersonation attempt in the attack matrix was correctly denied) |
| `iamcredentials.googleapis.com` is not required to be enabled for base WIF token issuance, only for explicit impersonation-style calls | Empirically confirmed | Neither project had this API enabled; ordinary WIF token issuance and the real sign call both worked regardless; impersonation attempts failed partly via `SERVICE_DISABLED` for this API, which is itself a valid, stronger denial (never enabled, consistent with least-privilege) |
| Cross-project GSA binding is supported: a GKE cluster's workload identity pool can back a GSA in a *different* project than the cluster's own project | Yes, empirically confirmed | The signer KSA (in `emg-platform-staging`'s cluster) was bound to a GSA in the separate `emg-ra-signer-wifqual-8a1323ba` project, and real token issuance + real `AsymmetricSign` both succeeded |
| IAM binding removal (revocation) is not instantaneous; propagation commonly takes on the order of a couple of minutes | Empirically confirmed this session (see `REVOCATION_TIMING.md`): a fresh credential-acquisition attempt still succeeded 31s after removal; a later fresh attempt was denied. Google's own general guidance documents IAM propagation as commonly ~2 minutes, up to ~7 minutes in some cases | `docs.cloud.google.com/kubernetes-engine/docs/troubleshooting/authentication` (general IAM propagation guidance); this session's direct measurement |
| An already-issued OAuth access token remains valid until its own natural expiry regardless of the underlying IAM/WIF binding being removed afterward | Empirically confirmed via `tokeninfo` | This session's direct measurement (see `REVOCATION_TIMING.md`) |
| Best-current guidance discourages static service-account key files in favor of Workload Identity Federation | Yes (well-established, consistent across all current GKE security documentation) | No key file was created or required anywhere in this qualification |

## Conclusion

No provider behavior found in this qualification contradicts ADR-044 or ADR-045. The real GKE Workload Identity Federation mechanism enforces the intended authority/signer capability separation correctly: identity is derived solely from the real, provider-verified `[namespace/KSA-name]` subject bound via an exact IAM policy, never from the locally-set `iam.gke.io/gcp-service-account` annotation alone (which is merely a hint to the metadata server, not itself a grant of capability).
